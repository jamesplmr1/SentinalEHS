# Sentinel EHS OpenAPI Documentation Conventions

## 1. Purpose

This document defines how Sentinel EHS generates, exposes, and maintains OpenAPI documentation for the HTTP API provided by `SentinelEHS.Api`.

The objectives are to:

- Provide an accurate, machine-readable description of the implemented API.
- Help frontend developers and integration consumers understand available endpoints and contracts.
- Reduce divergence between API implementation and API documentation.
- Avoid unnecessary exposure of runtime API metadata in production environments.
- Establish a foundation for future interactive documentation and external integration support.

---

## 2. OpenAPI Generation

Sentinel EHS will generate an OpenAPI specification from the implemented ASP.NET Core API.

The generated document should describe, where applicable:

- HTTP methods.
- Resource routes.
- Route and query parameters.
- Request contracts.
- Response contracts.
- HTTP response status codes.
- Authentication and authorisation requirements.
- Validation and error-response contracts.

OpenAPI documentation should derive from the implemented API wherever practical. Sentinel EHS should not rely on a separately maintained endpoint catalogue that can drift away from the application.

---

## 3. OpenAPI Version

Sentinel EHS will initially use the OpenAPI version generated by the standard .NET 10 ASP.NET Core OpenAPI implementation.

The OpenAPI version will not be overridden unless a confirmed compatibility requirement arises for an API consumer, documentation tool, client generator, or integration platform.

A framework default must not be replaced merely to introduce additional configuration.

---

## 4. Environment Exposure

The runtime OpenAPI document endpoint will be exposed in the Development environment.

The runtime OpenAPI document endpoint will not be exposed in Production by default.

This approach allows developers to inspect and validate the API contract locally while reducing unnecessary disclosure of endpoint and schema metadata in production.

If Sentinel EHS later provides a supported external integration API, production API documentation will be published through a deliberate and separately reviewed mechanism. Production publication must not be enabled simply by exposing the development endpoint.

---

## 5. Document Location

During local development, the generated OpenAPI document is expected to be available from the standard development endpoint:

```text
/openapi/v1.json
```

The exact local host name and port are determined by the active development launch profile.

The document name `v1` identifies the generated OpenAPI document. It does not introduce URL-based API versioning into Sentinel EHS resource routes.

For example, Sentinel EHS resource routes remain:

```text
/api/incidents
/api/sites
/api/hazards
```

They do not become:

```text
/api/v1/incidents
```

unless a separate API-versioning decision is made in the future.

---

## 6. Documentation Accuracy

The generated OpenAPI document must accurately reflect the implemented API.

Controllers and endpoint contracts should provide sufficient metadata for consumers to understand:

- The purpose of an operation.
- Required and optional input.
- Expected request structure.
- Successful response structure.
- Relevant failure responses.
- Whether authentication or a particular authorisation requirement applies.

Changes to routes, request contracts, response contracts, or expected status codes must be reflected in the generated OpenAPI document as part of the same implementation change.

An endpoint must not be considered fully documented when the generated contract materially disagrees with its runtime behaviour.

---

## 7. Request and Response Contracts

OpenAPI schemas will describe explicit Sentinel EHS API request and response contracts.

Domain entities and persistence entities must not be exposed directly merely to simplify OpenAPI generation.

The documented boundary remains:

```text
Domain Model
     ↓
Application Result
     ↓
API Request or Response Contract
     ↓
OpenAPI Schema
     ↓
API Consumer
```

This ensures that generated documentation reflects the public HTTP contract rather than internal implementation details.

---

## 8. Error Documentation

OpenAPI documentation should describe the standard error responses relevant to each operation.

Sentinel EHS API errors will use the agreed Problem Details representation.

Relevant operations should document expected outcomes including, where applicable:

- `400 Bad Request`
- `401 Unauthorized`
- `403 Forbidden`
- `404 Not Found`
- `409 Conflict`
- `500 Internal Server Error`

Error documentation must not reveal sensitive implementation information, tenant information, or the existence of records unavailable to the caller.

---

## 9. Security Documentation

OpenAPI documentation may describe that an endpoint requires authentication or a particular permission category, but generated documentation does not enforce security.

Runtime security remains the responsibility of Sentinel EHS authentication, tenant isolation, authorisation, and record-scope enforcement.

The security sequence remains:

```text
Authentication
      ↓
Tenant Context
      ↓
Tenant Membership
      ↓
Effective Permission
      ↓
Record and Site Scope
      ↓
Application Operation
```

Sensitive implementation details, internal claims, secrets, tokens, or tenant-specific configuration must not be included in the OpenAPI document.

---

## 10. Interactive Documentation

An interactive documentation interface is not required for the initial API foundation.

Tools such as Swagger UI or Scalar may be introduced later when Sentinel EHS contains sufficient implemented API functionality to make interactive exploration useful.

Any interactive documentation interface must:

- Use the generated OpenAPI document as its source.
- Be enabled only in explicitly approved environments.
- Avoid exposing production API metadata unintentionally.
- Respect the same authentication and security publication decisions as the underlying OpenAPI document.

The absence of an interactive interface does not mean that OpenAPI documentation is missing. The generated JSON document is the authoritative machine-readable specification.

---

## 11. Validation and Maintenance

OpenAPI documentation must be checked as API functionality evolves.

At minimum:

- The generated document must be retrievable in Development.
- The document must remain valid JSON.
- Implemented Sentinel EHS endpoints must appear with the correct HTTP method and route.
- Request and response schemas must match the public API contracts.
- Removed template endpoints must no longer appear.
- OpenAPI generation failures must fail development or CI validation once automated validation is introduced.

OpenAPI validation may later be added to continuous integration to detect invalid or unexpectedly changed API contracts.

---

## 12. Initial Verification

The initial ASP.NET Core API host has been verified to generate an OpenAPI document successfully in the Development environment.

The document was retrieved from:

```text
/openapi/v1.json
```

This confirms that the initial OpenAPI generation and development endpoint are operational.

The template WeatherForecast endpoint remains temporary and must be removed before the API foundation is considered representative of Sentinel EHS functionality.

---

## 13. Definition of Done

The OpenAPI documentation task is complete when:

1. OpenAPI generation is registered for `SentinelEHS.Api`.
2. The generated OpenAPI document is available in the Development environment.
3. The document is not exposed in Production by default.
4. The generated document is valid JSON.
5. The generated document reflects the implemented Sentinel EHS controller routes and contracts.
6. The standard .NET 10 OpenAPI version is retained unless a documented compatibility requirement justifies changing it.
7. The temporary WeatherForecast endpoint is removed from the generated document when the template code is removed.
8. The complete solution builds successfully.
9. The OpenAPI conventions are stored in the repository and referenced from the relevant Azure Boards work item.

---

## 14. Convention Summary

Sentinel EHS will:

- Generate OpenAPI documentation from the implemented ASP.NET Core API.
- Use the standard .NET 10 OpenAPI behaviour unless a confirmed requirement justifies deviation.
- Expose the runtime OpenAPI document in Development only by default.
- Use explicit API request and response contracts as OpenAPI schemas.
- Document relevant success, validation, security, and conflict responses.
- Treat OpenAPI as documentation rather than a security control.
- Defer interactive documentation until it provides practical development value.
- Maintain the generated contract alongside API implementation changes.
